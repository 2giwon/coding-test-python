## 1 — 해시 또는 정렬 · 🟢 학습 완료 유형

**정답은 두 가지다. 둘 다 통과한다.**

| | |
|---|---|
| **신호** | "두 목록의 차이를 찾는다" + 🔴 **"동명이인이 있을 수 있다"** |
| **확정 조건** | 길이 10만 → 이중 for문(100억) 불가 |

### 정답 ① 해시 — `collections.Counter`

```
Counter(참가자) - Counter(완주자)  →  남는 키가 답
```

### 정답 ② 정렬 — 양쪽을 정렬해 앞에서부터 비교

```python
participant.sort()
completion.sort()
for p, c in zip(participant, completion):
    if p != c:
        return p          # 줄이 어긋나는 지점이 답
return participant[-1]    # 끝까지 같으면 마지막 사람
```

**왜 되는가** — 정렬하면 같은 이름끼리 붙어 선다.
완주자 쪽에 한 명이 모자라므로 **그 지점부터 줄이 한 칸 밀린다.**

```
참가자  정렬 →  ana  mislav  mislav  stanko
완주자  정렬 →  ana  mislav  stanko
                            ↑ 여기서 어긋남 → mislav
```

동명이인을 따로 처리하지 않아도 자동으로 맞는 것이 이 풀이의 장점이다.

| | 해시 `Counter` | 정렬 비교 |
|---|---|---|
| 10만명 실측 | 0.009초 | 0.023초 (둘 다 여유) |
| 외울 것 | `Counter` 뺄셈 | 🟢 없음 |
| 코드 | 1줄 | 5줄 |
| "완주 못한 사람 **전부**"로 바뀌면 | 🟢 그대로 통함 | 🔴 손봐야 함 |

### 🔴 "동명이인"이 이 문제의 함정이다

이 한 단어가 `set` 을 탈락시킨다. 집합은 중복을 버린다.

```
참가자 = [홍길동, 홍길동, 김철수]
완주자 = [홍길동, 김철수]

set(참가자) - set(완주자)  →  빈 집합   🔴 답이 안 나온다
```

> **외울 한 줄**: 있다/없다만 보면 `set`, **몇 개인지 세야 하면 `Counter`**.
> 지문에 "중복 / 동명이인 / 같은 값이 여러 개"가 있으면 `set` 은 즉시 탈락.

### 🔴 오답 — "정렬 후 마지막 원소 반환" (2026-10-20 실제로 나온 답)

```python
return sorted(participant)[-1]      # 🔴 틀렸다
```

**근본 문제: 완주자 명단을 한 번도 쓰지 않는다.**
입력의 절반을 버리고 답을 내는 코드는 구조적으로 맞을 수 없다.
정렬은 순서만 바꿀 뿐, **누가 빠졌는지는 반드시 완주자 명단과 맞춰봐야** 알 수 있다.

가장 작은 반례:

```
참가자 = [a, b]   완주자 = [b]
  정답 = a
  이 방식 = b      🔴
```

🔴 **그런데 이 오답이 공식 예제 3개 중 2개를 통과한다** (2026-10-20 실측).

```
프로그래머스 공식 예제 3개 중   2개 통과   🟡 위험
무작위 20,000건                10,561건 틀림 (52.8%)   🔴
```

→ 예제만 돌려보고 "맞았다"고 판단하면 절반이 틀린 코드를 들고 제출한다.
이것이 `career-transition/README.md` W2~W6 의 **"채점 통과 ≠ 정답"** 과 같은 계열이다.

## 2 — 힙 · 🟢 학습 완료 유형 (10/13 더 맵게와 같은 구조)

**정답: 최소 힙 (`heapq`)**

| | |
|---|---|
| **신호** | **"매번 가장 작은 두 개를 꺼내 합치고, 결과를 다시 넣는다"** |
| **확정 조건** | N = 10만 → 매번 정렬하면 시간초과 |

🔴 **더 맵게(42626)와 구조가 완전히 같다.** 이름만 다르다.

| | 더 맵게 | 이 문제 |
|---|---|---|
| 꺼내는 것 | 가장 안 매운 2개 | 가장 작은 묶음 2개 |
| 합치는 식 | `a + b*2` | `a + b` |
| 다시 넣기 | 넣는다 | 넣는다 |
| 멈추는 조건 | 최솟값 ≥ K | 묶음이 1개 남음 |

→ 이걸 못 맞혔다면 **문제 이름에 묶여 있다는 신호**다.
힙의 신호는 "작은 것 2개를 꺼내 다시 넣는 순환"이지 "매운 음식"이 아니다.

## 3 — BFS · 🟢 학습 완료 유형

**정답: BFS (너비 우선 탐색)**

| | |
|---|---|
| **신호** | **"격자" + "최소 칸 수"** |
| **확정 조건** | 가중치가 없다(모든 이동 비용 1) → 다익스트라가 아니라 BFS |

🔴 **"최소"와 "격자"가 같이 나오면 거의 항상 BFS다.**
DFS는 최단거리를 보장하지 못한다 — 먼 길로 먼저 들어가면 그게 답이 되어버린다.
BFS는 거리 1인 칸을 전부 본 뒤 거리 2로 넘어가므로, **처음 도착한 순간이 최단**이다.

이미 푼 미로탈출(`06-bfs-dfs/`)과 같은 문제다.

## 4 — 정렬 (커스텀 key) · 🟡 학습 완료 유형이지만 함정 있음

**정답: 정렬 — 비교 기준을 바꾼 정렬**

| | |
|---|---|
| **신호** | **"이어붙여 만들 수 있는 가장 큰 수"** = 순서만 정하면 끝 |
| **확정 조건** | 길이 10만 → 모든 순서를 다 해보는 것(순열)은 불가 |

🔴 **그리디라고 답했다면 절반만 맞았다.** 실제로 이건 "그리디의 근거를 가진 정렬"이다.
하지만 코테에서 손이 가야 하는 건 **정렬 한 줄**이다.

```python
sorted(map(str, numbers), key=lambda x: x * 3, reverse=True)
```

**왜 `x * 3` 인가** — 원소가 최대 1,000(4자리)이라
`"3"` 과 `"30"` 처럼 길이가 다른 두 수를 비교할 때 길이를 맞춰야 한다.
`"333" vs "303030"` 으로 늘려 비교하면 `"3"` 이 앞에 와야 함을 알 수 있다(3+30=330 > 303).

- 🔴 함정: 전부 0이면 `"0000"` 이 나온다 → `int()` 로 변환 후 다시 문자열로.

원본: 프로그래머스 42746 가장 큰 수 (`04-sort/` 유형)

## 5 — 🔴 이진탐색 (파라메트릭 서치) · **미착수 유형**

**정답: 파라메트릭 서치 (답을 가정하고 검사하는 이진탐색)**

| | |
|---|---|
| **신호** | **"최소 시간"을 구하는데, 그 시간을 직접 계산할 공식이 없다** |
| **확정 조건** | 🔴 **n이 10억**. 사람을 하나씩 배정하는 시뮬레이션은 애초에 불가능 |

🔴 **이 유형의 신호는 "제약 조건의 숫자가 비정상적으로 크다"는 것이다.**
n = 1,000,000,000. 10억 번 반복은 어떤 방법으로도 못 한다.
→ **구할 수 없으면 찍어서 검사한다.**

사고의 전환이 이것이다.

```
❌ "최소 시간은 얼마인가?"            ← 직접 못 구한다
🟢 "시간 T 안에 n명을 처리할 수 있나?"  ← 이건 쉽다 (T // 각 심사시간 을 전부 더함)
```

뒤의 질문은 **T가 커지면 답이 예→예, 작아지면 아니오→아니오로 한 방향**이다.
이렇게 단조로우면 T를 이진탐색으로 좁힐 수 있다.

```
lo = 1, hi = (가장 느린 심사관) × n
while lo < hi:
    mid = (lo + hi) // 2
    처리 가능하면 hi = mid    (더 줄여본다)
    안 되면      lo = mid + 1
→ lo 가 답
```

**이 유형이 로드맵에서 힙 다음, 문자열 바로 뒤에 있는 이유**가 여기 있다.
신호가 "큰 숫자 + 최소/최대"로 명확해서 투자 대비 회수가 크다.

원본: 프로그래머스 43238 입국심사 → `10-binary-search/` 1단으로 쓸 예정

## 6 — 🔴 그리디 · **미착수 유형**

**정답: 정렬 + 양쪽에서 좁히기(투포인터) 그리디**

| | |
|---|---|
| **신호** | **"최소 개수"** + **"보트 하나에 최대 2명"** (짝을 짓는 문제) |
| **확정 조건** | 길이 5만. 정렬 O(n log n) 후 한 번 훑으면 끝 |

🔴 **그리디는 신호가 흐린 유형이다**(이게 로드맵 후반에 있는 이유).
그래도 이 문제는 비교적 선명하다 — **"최소 개수로 짝짓기"** 가 그 표지다.

판단의 핵심: **가장 무거운 사람은 어차피 보트를 하나 차지한다.**
그러면 그 보트에 **가장 가벼운 사람을 태울 수 있으면 태우는 게 항상 이득**이다.
(안 태우면 그 가벼운 사람이 나중에 보트를 또 하나 쓴다)

```
정렬 → 양 끝에서 시작
가장 가벼운 + 가장 무거운 ≤ 제한  →  둘 다 태운다 (양쪽 포인터 이동)
초과                            →  무거운 사람만 혼자 (오른쪽만 이동)
보트 수 += 1
```

🔴 **그리디에서 가장 중요한 건 "왜 그게 최선인지 말할 수 있는가"다.**
위 두 줄("어차피 보트 하나를 쓴다 / 안 태우면 나중에 또 쓴다")이 그 증명이다.
증명 없이 감으로 그리디를 쓰면 틀린다 — 이 유형이 위험한 이유다.

원본: 프로그래머스 42885 구명보트 → `09-greedy/` 1단 후보

## 7 — 🔴 문자열 (순차 처리) · **미착수 유형 — 오늘 착수**

**정답: 문자열 단계별 처리 (정규식 또는 순수 파이썬)**

| | |
|---|---|
| **신호** | **"아래 단계를 순서대로 적용하라"** — 규칙이 이미 다 적혀 있다 |
| **확정 조건** | 길이 1,000. 성능 문제가 없다 → 알고리즘이 아니라 **정확성** 문제 |

🔴 **이 유형은 "무엇을 쓸까"가 아니라 "빠뜨리지 않았나"가 전부다.**
지문에 답이 이미 적혀 있으니 떠올릴 게 없다. 대신 함정이 많다.

| 단계 | 🔴 틀리는 지점 |
|---|---|
| 3 | `"..."` → `"."` 은 **반복 치환**이 필요하다. 한 번만 바꾸면 `"...."` → `".."` 로 남는다 |
| 4 | 3단계 후에 또 `.` 이 끝에 생길 수 있다. **순서를 지켜야 한다** |
| 6 | 15자로 자른 **뒤에** 끝이 `.` 인지 다시 본다. 자르기 전에 보면 틀린다 |
| 7 | "마지막 문자"를 반복한다. 첫 문자가 아니다 |

**카카오 1번 단골 유형이다.** 어렵지 않지만 단계를 하나 빼먹으면 0점이라,
"빠뜨리지 않는 절차"를 몸에 익히는 게 목적이다.

원본: 프로그래머스 72410 신규 아이디 추천 → `02-string/` 2단 후보

## 8 — 🔴 **함정 — 도구가 필요 없다**

**정답: 전탐색(이중 for문) + `set` + `sorted`**

| | |
|---|---|
| **신호** | 🔴 **배열 길이가 2 ~ 100 뿐이다** |
| 계산량 | 100 × 100 = 10,000번. 1초에 수천만 번 도는 파이썬에게 아무것도 아니다 |

```python
sorted({numbers[i] + numbers[j]
        for i in range(len(numbers))
        for j in range(i + 1, len(numbers))})
```

🔴 **"두 수의 합"을 보고 해시나 투포인터를 꺼냈다면 과잉이다.**
그 기법들은 길이가 10만 이상일 때 필요한 것이다. 여기서는 코드만 길어지고 틀릴 자리만 늘어난다.

**이 문항이 측정한 것**: 제약 조건의 숫자를 실제로 봤는가.

지금까지 제약 조건은 늘 **"무엇을 쓰라"는 신호**로 쓰였다(길이 10만 → 힙/스택).
그런데 **"아무것도 쓰지 말라"는 신호**로도 쓰인다. 작은 숫자는 전탐색 허가증이다.

이건 이미 겪은 교훈과 같은 계열이다 — 10/13 더 맵게에서
"무한루프가 걱정돼서" 불필요한 특수 케이스를 심었다가 반례 4개를 만들었다.
**필요 없는 것을 넣으면 그게 새 버그가 된다.**

# 🔴 제약 조건 → 허용 계산량 (드릴 01 의 최대 수확)

2026-10-20 드릴에서 **8문항 8개 전부** 제약 조건의 숫자가 판단 근거에 들어가지 않았다.
유형 지식이 빈 게 아니라 **이 표를 안 보는 습관**이 원인이었다.

| 제약 n | 써도 되는 것 | 대략 계산량 |
|---|---|---|
| n ≤ 10 | 🟢 **순열 전탐색** | n! |
| n ≤ 20 | 🟢 **부분집합 전탐색** | 2ⁿ |
| n ≤ 500 | 삼중 for | n³ |
| n ≤ 5,000 | 이중 for | n² |
| n ≤ **100,000** | 🟢 **정렬 · 힙 · 해시** | n log n |
| n ≤ 10,000,000 | 한 번 훑기 | n |
| n ≥ **1억** | 🔴 **이진탐색 · 수식만** | log n |

## 문제를 받으면 이 순서로 한다

```
1. 🔴 제약 조건의 숫자를 먼저 본다      ← 지문보다 먼저
2. 그 숫자가 허용하는 계산량을 정한다
3. 그 안에서 되는 도구만 후보로 남긴다
4. 그다음에 지문을 읽는다
```

## 🔴 "완전탐색"은 n ≤ 20 전용이다

드릴 01 에서 8문항 중 **4문항**(2·4·7·8번)에 "완전탐색"이라고 답했고, **8번만 맞았다.**
넷을 가른 것은 제약 숫자다.

| 문항 | 답 | 제약 | 실제 정답 | 판정 |
|---|---|---|---|---|
| 2 | 완전탐색 | 10만 | 힙 | 🔴 |
| 4 | 완전탐색 | 10만 | 정렬 | 🔴 |
| 7 | 완전탐색 | 1,000 | 구현(시뮬레이션) | 🟡 이름만 틀림 |
| 8 | 완전탐색 | **100** | 전탐색 | 🟢 |

→ 도구를 **고른** 것이 아니라 **기본값을 낸** 것이다.
그 기본값이 유효한지는 위 표로 1초에 판정된다.

## 🔴 "완전탐색"과 "구현"은 다르다

| | 완전탐색 | 구현 (시뮬레이션) |
|---|---|---|
| 하는 일 | 가능한 경우를 **다 시도해서 찾는다** | 정해진 절차를 **그대로 실행한다** |
| 선택지 | 있다 | **없다**(지문이 다 정해줬다) |

**고를 게 없으면 탐색이 아니다.** 지문에 절차가 번호로 적혀 있으면 구현이다(7번).
